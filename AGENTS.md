# Руководство для агентов

## Обзор проекта

`tinyrenderer` — учебный программный растеризатор на Go. Весь исходный код находится в корне репозитория и принадлежит одному пакету `main`; подпакетов и внутренних модулей нет.

Основной сценарий в `main.go` загружает одну или несколько OBJ-моделей, раскрашивает каждый треугольник случайным цветом, растеризует сцену в память и сохраняет изображение `out/framebuffer.png`. Размер кадра — 800×800. Без аргументов используется `diablo3_pose.obj`; пути к другим моделям можно передать аргументами командной строки.

Это CPU-рендерер, а не OpenGL-приложение: имя `gl.go` и тип `Renderer` обозначают собственную реализацию графического конвейера. Дополнительный оконный просмотрщик на Ebitengine находится в `viewer.go`, но в текущем рабочем дереве его интеграция не завершена (см. раздел о состоянии сборки).

## Конфигурация и зависимости

- `go.mod` — модуль `tinyrenderer`, версия Go `1.26.3`.
- `go.sum` — контрольные суммы зависимостей.
- Единственная прямая внешняя зависимость — `github.com/hajimehoshi/ebiten/v2 v2.10.5`, используемая только оконным просмотрщиком.
- `Taskfile.yml` — необязательные команды для Task (`go-task`); те же операции можно выполнять напрямую через Go CLI.
- `.gitignore` исключает каталоги `/out/` и `/.task/`.
- Конфигураций линтера, форматтера, CI, контейнеров или развёртывания в репозитории нет.

## Устройство кода

- `main.go` — точка входа, настройка камеры и viewport, цикл по моделям и граням, `RandomShader`, запись PNG. Локальные переменные `eye`, `center` и `up` задаются внутри `main`.
- `geometry.go` — типы `Vec2`, `Vec3`, `Vec4`, `Mat3`, `Mat4` и операции над ними. Матрицы хранятся по строкам; векторы и матрицы передаются по значению.
- `objmodel.go` — `Model` и `readModel`. Поддерживаются вершины `v x y z` и только треугольные грани вида `f v/vt/vn v/vt/vn v/vt/vn`. Индексы OBJ положительные и начинаются с единицы; текстуры и нормали не загружаются, остальные строки OBJ игнорируются. После чтения проверяются границы индексов вершин.
- `gl.go` — состояние и основные этапы рендерера: `LookAt`, центральная перспектива, viewport, преобразование clip → NDC → screen, отсечение задних граней, барицентрическая растеризация и z-buffer. `IShader` содержит только метод `Fragment`; вершинное преобразование в основном сценарии выполняет конкретный `RandomShader.Vertex`.
- `line.go` — целочисленный алгоритм Брезенхема для отрезков.
- `tgaimage.go` — собственный буфер изображения `TGAImage`, форматы Grayscale/RGB/RGBA, чтение и запись пикселей, вывод несжатого TGA и PNG.
- `viewer.go` — незавершённый цикл Ebitengine с вращением камеры и копированием кадра в окно. Основной `main` сейчас не вызывает `show`.
- `main_test.go` — тест и бенчмарк Брезенхема; других тестовых файлов нет.
- `diablo3_pose.obj` — модель по умолчанию.

`TGAImage` использует начало координат в левом нижнем углу. `TGAColor` хранит каналы в порядке BGRA, а `NewColor` принимает RGBA. При записи PNG строки переворачиваются по вертикали.

Растеризация каждого треугольника распараллеливается по непересекающимся диапазонам строк с количеством работников до `runtime.NumCPU()`. Поэтому реализации `IShader.Fragment` не должны изменять общее состояние без синхронизации: метод вызывается из нескольких горутин. Для каждого вызова `Rasterize` используется отдельная группа работников.

## Сборка и запуск

Команды выполняются из корня репозитория:

```sh
mkdir -p out
go build -o out/tinyrenderer .
./out/tinyrenderer                 # diablo3_pose.obj
./out/tinyrenderer path/to/a.obj  # одна или несколько моделей
```

Результат основной программы — `out/framebuffer.png`. Описание задачи `run` в `Taskfile.yml` упоминает TGA, но фактический `main.go` записывает PNG; метод `WriteTGAFile` доступен для других сценариев.

При установленном Task доступны:

```sh
task build       # out/tinyrenderer
task run         # сборка и запуск
task clean       # удаление всего out/
```

Бинарники `tinyrenderer` в корне и `out/tinyrenderer` могут быть ранее собранными артефактами; успешный запуск такого файла не подтверждает сборку текущих исходников.

## Тесты, бенчмарки и профилирование

```sh
go test ./...
go test -bench=. -benchmem
go test -bench=BenchmarkLine$ -benchmem
```

Единственный тест `TestLine` проверяет концы отрезков, число закрашенных пикселей и непрерывность для диагональных, горизонтальных, вертикальных, обратных, пологих, крутых и вырожденных линий. `BenchmarkLine` измеряет случайные отрезки в буфере 64×64. Новые тесты следует размещать в том же пакете `main`, чтобы при необходимости проверять неэкспортируемые функции напрямую. Для растеризатора, геометрии, OBJ и изображений автоматических тестов пока нет.

Задачи Task для производительности:

```sh
task bench
task bench BENCH=BenchmarkLine$
task profile BENCH=BenchmarkLine$  # out/cpu.prof и out/tinyrenderer.test
task pprof:top                     # 15 самых горячих функций
task pprof PORT=8080               # веб-интерфейс; требуется Graphviz
```

`profile` выполняет бенчмарк в течение трёх секунд. `pprof` и `pprof:top` сами заново запускают `profile` через зависимость Task.

## Стиль и соглашения

- Основной язык комментариев, сообщений тестов и документации — русский; идентификаторы — английские.
- Перед завершением изменений используйте `gofmt`; текущие Go-файлы отформатированы.
- Соблюдайте существующую плоскую структуру пакета `main`, именование `CamelCase` для экспортируемых API и `camelCase` для внутренних деталей.
- В коде приняты небольшие методы на значимых типах, составные литералы векторов и матриц, явная проверка и обёртывание ошибок ввода-вывода.
- При изменении геометрии учитывайте строковое представление матриц, порядок умножения `Perspective * ModelView`, нижнее левое начало координат и BGRA-представление пикселей.
- Не добавляйте зависимости без необходимости: базовый конвейер использует стандартную библиотеку, Ebitengine нужен только просмотрщику.

## Текущее состояние сборки

На момент составления этого руководства `go build ./...` и `go test ./...` завершаются ошибкой компиляции из-за `viewer.go`: не определены `Scene`, `center`, `eye` и метод `TGAImage.CopyTo`. Это не ошибки теста `TestLine`: пакет не доходит до выполнения тестов. До завершения интеграции просмотрщика нельзя считать обычные команды сборки, запуска, тестов и бенчмарков успешными. Старые бинарники не устраняют эту проблему.

## Границы и безопасность

Приложение обрабатывает локальные OBJ-файлы и пишет результат в фиксированный путь внутри `out/`; сетевого сервиса и процесса развёртывания нет. Парсер OBJ не является универсальным: не расширяйте негласно поддерживаемый формат при не связанных с этим изменениях. Пути моделей приходят из аргументов пользователя, поэтому ошибки открытия и разбора должны возвращаться с понятным контекстом, а не игнорироваться.

Перед завершением содержательного изменения запускайте как минимум `gofmt` и `go test ./...`, а для меняющего производительность кода — соответствующий бенчмарк. Не удаляйте и не перезаписывайте пользовательские изменения в `go.mod`, `go.sum` или `viewer.go` ради обхода текущей ошибки сборки.
